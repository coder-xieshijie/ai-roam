这个项目开始于一次内部实验：能不能用一天时间，做出一个同时支持 Mac 和 Windows 的桌面客户端。

结果是半天。我作为后端开发，选的技术栈之前从没用过，甚至没了解过。全程在终端里和 Agent 交互，没有打开编辑器，没有写一行代码，也没有改任何环境配置。最费时间的是一开始的技术栈选择和功能设计。

同一个需求，我试了两种给法：

  • 粗糙的初始需求，逐步澄清：大约十几轮对话，3 小时左右，token 花费约 50 美元。时间主要花在等代码生成和人工验证上。
  • 先把需求汇总完整，再一次性给出：2 轮对话交付，30 分钟左右，花费 10 多美元。

清晰完整的需求能明显提升交付速度和质量，这件事越早做越好。

之后项目进入快速迭代，参与的人越来越多，每个人用的 Agent 也不一样：Claude Code、Codex、OpenCode。新的问题随之出现：Agent 能很快堆出功能，却不知道代码会扩散到哪里、打破什么约束。

Agent 最常犯的两类错

一是跨层依赖，也就是架构漂移。我们设计了 a、b、c 三层，Agent 实现时直接让 a 依赖 c。

二是重复实现。仓库里已经有类似的实现，它还是自己再写一个。

不同 Agent 对代码和文档的理解不同，生成风格和架构倾向也不同；不同的人用同一个工具，结果也有差异。靠口头约定管不住，只能靠硬性卡点，把软约束编码成规则。

架构约束：从文档到代码

架构约束的沉淀，大致走了三步。

第一步，所有规范都写在一份 AGENTS.md 里。 很快发现不行：上下文是稀缺资源，大而全的文档，大部分内容和当前任务无关。

第二步，拆成各模块的 README、AGENTS.md 和 Skill。 设计原则是：

  • 不要追求大而全；
  • 渐进式加载，用专门的 docs 目录存放 spec；
  • 给一个索引，而不是全部说明；
  • 文档和 Skill 都可以设计成按需加载。

第三步，代码化。 能自动检查的规则，全部迁移到 ESLint：分层依赖、React 引用、循环引用。

在以人为主的开发里，强制规定可能显得束缚甚至迂腐；在 Agent 时代，它是倍增器。

ESLint 规则是怎么长出来的

核心只有一点：Agent 的每一次犯错，都要变成一个工程化方案。

规则从初始化的一组开源规则开始，之后每发现一类错误，就补一条：

  • 禁止在类型位置动态导入。 Agent 经常在类型声明里写 import("./path").Type，这会导致循环依赖。一个是编译时确定，一个是动态加载、返回 Promise，混在一起容易出问题。第 7 轮迭代，我们用 AST 选择器检查并禁止了这种写法。
  • 禁止 setInterval。 Agent 频繁使用 setInterval，容易造成内存泄漏。第 8 轮迭代全局禁止了它，同时在共享包里提供 createInterval() 作为替代。不只是禁止，而是给出替代方案。
  • 统一报错格式。 所有 Error Message 统一成“原因：xxx。解决：xxx。”这让每个 lint 错误都成为给 Agent 的实时教学：它不仅知道做错了什么，还知道怎么修。

一条跨层规则大致长这样（示意）：

"no-restricted-imports": ["error", {
  patterns: [{
    group: ["**/ui/**"],
    message: "原因：service 层不能依赖 ui 层。解决：把共享类型移到 types 层再引用。",
  }],
}]

约束的两种形态

做下来，我把约束分成两种：

  • 计算型约束：规则、ESLint、类型检查。确定、便宜、每次都执行。
  • 大模型约束：需要 AI 参与，比如本地 CR、架构扫描之类的 Skill。能判断更复杂的问题，但结果不完全确定。

反馈回路也按层级排开：代码生成 → ESLint / TS 检查 → CI/CD → Agent Review → 人工 Review 和功能回归。越往后越贵，所以能前移的尽量前移。

当 Agent 走歪了，纠偏也有四层：linter、spec 与 TDD、CR review、架构 review。

MR 超过 2000 行，不准合入

我们给合并请求设了几道卡点：关联需求、附功能描述和截图、带单测、限制单次代码量。

其中行数限制背后是一个判断：

  • 如果一个需求需要 2000 行才能完成，错的不是 Agent，而是 harness；
  • 当 MR 的质量持续下降，应该着手修复 harness 的约束、文档和工具，而不是加强人工审查；
  • 当 MR 需要大量修复，或者本身内容很多，都是 harness 设计的问题。

还做得不够的地方

  • 功能正确性。 现在的约束主要保护内部质量和可维护性，对功能是否正确覆盖得很少。常见的风险是：行为看似正确，但藏着 bug；测试通过，但功能是坏的，因为 Agent 倾向于修改测试，而不是修复代码。
  • 规则还有一部分停留在文档里。 文档转代码做得不够彻底。
  • 文档腐化。 AI 生成的文档过时得很快，需要定期治理，和死代码、重复代码、过期代码一起清理。

回头看这一个月，我的工作方式变了。最开始是 human in the loop，和 Agent 一起写；后来一度 out of the loop，放任它发挥；现在是 on the loop：构建和维护 Agent 的控制环境。

人不是不写代码了，而是从更高的层面约束 AI：架构、质量门禁、规则。发现问题时，不是让 AI 更努力，也不是替 AI 完成，而是想办法设计流程，让它清晰准确地参与其中。
