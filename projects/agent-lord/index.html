AGENT ORCHESTRATION · 起点

Agent Lord

这条工作流的起点：一个在主会话里调度多个编程 Agent 的工具。
8 月写成，把任务派给 Claude Code、Codex 和 MCode，让它们并行干活、互相评审，每一步都有记录。用下来发现，卡住交付的不是 Agent 不够多：它们没法自己运行产品来证明做对了，已经定下的事也会在一次次交接中丢失。9 月底起，新需求改走 dev-skills 的流程。

它是什么

在 Codex、Claude Code 或 MCode 的一个主会话里，把工作派给 Claude Code、Codex CLI、MCode CLI 或 Codex App 任务。Agent Lord 保存执行设置、会话、进度和产物，主会话可以监督这些任务，并在后续轮次接着推进。

它由三部分组成：指导主会话的 Skill、负责执行与记录的 CLI runtime，以及展示进度的 Observer。拆分任务、派发和验收都由主会话负责；执行端可以用自己的工具和子 Agent，但不能再调用 Agent Lord。

做过的几条 pipeline

常用的多会话流程被固定成 pipeline：谁来做、哪些能并行、什么证据能放行下一步、什么时候结束。

  1. 交叉评审

    MCode 与 Codex 先各自独立评审，再交换结论互相质证；最后由一个新的 MCode 会话逐项独立裁决。流程是否走完、代码有没有问题，分开报告。

    阅读 pipeline 规则 ↗

  2. 计划交叉评审

    两个评审者交叉质证后，由一个新的复核者核对问题与方案，并重写完整计划；再由另一个新会话对照需求与源码验证。作者不自查最终文档。

    阅读 pipeline 规则 ↗

  3. 计划到实现

    写代码前先定下验收场景；按计划阶段在一条分支上顺序实现，每个阶段一个会话；最后的评审和验收跑在同一个 head 上。获得授权后，每个仓库开或更新一个 PR/MR；流程不会合入。

    阅读 pipeline 规则 ↗

执行成功、交付物存在、测试通过和代码正确，是分开判断的结果。交叉评审把“流程是否走完”和“代码有没有问题”分开报告；计划到实现会开 PR/MR，合入仍由人决定。

为什么不再用于新需求

Agent Lord 解决的是同时调度多个 Agent。用下来，卡住交付的是另外两件事：Agent 没法自己运行和操作正在开发的产品，问题常常要等我自己用的时候才发现；已经定下的决定，也会在一次次交接中丢失。Agent 越多，要我检查和重复说明的事越多。

9 月底起，新需求改走 dev-skills 的流程：先给仓库搭一个 Agent 能自己启动、操作、观察的验证环境；再由一个 Agent 负责到底，需要并行时由它自己分给子 Agent；最后由另一家模型独立验证。让不同模型互相检查的做法，在新流程里留了下来。

使用前了解的边界

Observer 不发起任务，也不推进 pipeline；在用户明确要求时，可以打开已有 CLI 会话的终端入口。Codex App 端点只展示任务状态，CLI 端点可展示会话与工具活动。

引用版本的 Skill 会以权限跳过模式启动新 CLI 任务。“只评审、不修改”属于任务指令，不能把执行进程变成只读沙箱。首次运行前应读清执行约定，选择合适的工作目录与授权范围。

阅读执行约定 · 本地验证平台为 macOS，CI 覆盖 macOS 与 Linux；项目未声明完成 Windows 端到端验证。
